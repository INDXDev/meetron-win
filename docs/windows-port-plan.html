Platform migration study

Meetron on Windows

A codebase audit and staged plan for shipping a genuinely native Windows build of the ChatGPT Voice ↔ meeting bridge — without rewriting the parts that already work.

Repo bb8ad8/meetron @ 8721658 Version 0.10.1 Audited 31 Aug 2026 Scope full tree, 15,451 non-test LOC
01

The finding

Meetron is far more portable than its "os": ["darwin"] manifest suggests. The entire meeting-automation brain — providers, protocol, session orchestration, ChatGPT driving, audio routing, the Chrome extension — is platform-neutral JavaScript that talks to Chrome over CDP and never touches an OS API. Roughly 53% of Meetron's own code moves to Windows with zero edits.

The macOS dependency is concentrated in exactly two places: a virtual audio driver and 3,082 lines of bash doing process and installer plumbing. The bash is a mechanical port. The driver is the whole project.

1Genuinely hard problemTHE VIRTUAL AUDIO DEVICE

Three facts from the audit shape everything that follows.

The audio bridge already lives in the browser, not in the OS. scripts/prepare-chatgpt-live.mjs and scripts/prepare-zoom.mjs override MediaDevices.prototype.getUserMedia and setSinkId inside the page to pin each tab to a named device. macOS system defaults are deliberately never changed — getAudioStatus() literally returns systemDefaultsUnchanged: true. All the OS has to supply is two audio endpoints whose labels start with Meetron: Meeting to AI and Meetron: AI to Meeting. Everything above that line is already cross-platform.

Screen sharing needs no OS permission at all. "Send screen to GPT" is page.screenshot() over CDP on the meeting tab (src/chatgpt/chatgpt-web.mjs:405), not a system screen capture. There is no ScreenCaptureKit dependency, so there is no Windows Graphics Capture work to do. That removes what would normally be the second-hardest item on a port like this.

The platform seam already exists — it is just too narrow. src/platform/platform-contract.mjs defines a real adapter interface, and tests/platform-contract-test.mjs:36 already asserts that getPlatformAdapter("win32") throws. The design anticipated this port. The adapter currently carries two things (paths and a mute shortcut); it needs to carry about eight.

02

How Meetron is built

Meetron has no native application. The user interface is a Chrome extension: a popup wizard plus a panel injected onto the Meet/Zoom page. That extension talks over Chrome Native Messaging to a Node.js host, which drives a second, dedicated Chrome instance over CDP using Playwright. Two virtual audio devices carry sound between the two Chrome instances.

Portability audit

Every file in the tree falls into one of three buckets. Line counts are measured, and exclude the 4,141-line test suite.

Moves unchanged

5,916 LOC · 53% of Meetron's own code

  • src/core/* — protocol, session state, orchestrator, participant state (452)
  • src/providers/* — Meet + Zoom Web automation (1,070)
  • src/chatgpt/chatgpt-web.mjs — Voice control, screenshot attach (534)
  • src/browser/, src/audio/ contracts (184)
  • src/platform/*.mjs contracts + registry (117)
  • extension/* — the entire UI (1,631)
  • scripts/prepare-*.mjs — page injection (1,621)

Needs an adapter seam

1,638 LOC · refactor, then reuse

  • scripts/native-host.mjs (1,015) — /bin/ps, POSIX signals, process groups, 0o600 modes, Homebrew PATH
  • scripts/audio-backend.mjs (301) — hardcoded meetron-audioctl / SwitchAudioSource paths
  • scripts/verify-dedicated-chrome.mjs (85) — ps + lsof for the CDP port ownership check
  • scripts/meeting-start-job.mjs, session-launch.mjs (237) — detached spawn and exit-code contract

Must be rebuilt

4,815 native + 3,082 bash

  • native/audio-driver/ — CoreAudio AudioServerPlugIn, 4,273 lines derived from Apple's sample + a 149-line ring buffer
  • native/audio-control/ — Swift CoreAudio CLI (347)
  • scripts/*.sh (2,461), native/audio-driver/*.sh (536), *.command (85)
  • src/platform/macos/ (46) — gains a windows/ sibling

The middle bucket is the interesting one. Those four files are Node.js already — they just reach for POSIX primitives inline instead of going through the adapter. Widening the contract turns them into shared code, which means the refactor pays for itself on macOS too: one implementation, two platforms.

05

The critical path: getting audio into Chrome

Every other item on that table is a week or less. This one decides the project. macOS lets you ship a virtual audio device as an unprivileged user-mode bundle; Windows does not. There is no user-mode equivalent of AudioServerPlugIn — an audio endpoint on Windows is a kernel driver, full stop.

Meetron needs two directions. Capturing meeting audio out of Chrome could be done driverless with WASAPI process loopback. But feeding ChatGPT's voice into Chrome as a microphone is the hard half: getUserMedia only enumerates real capture endpoints. Three ways out, in the order I would attempt them.

Option C

Ship on an existing virtual cable

Recommended for bring-up

Depend on VB-CABLE, Virtual Audio Cable or VoiceMeeter for the beta, exactly as Meetron already depends on BlackHole for migrating macOS users. AUDIO_BACKENDS in scripts/audio-backend.mjs gains one more entry and nothing else changes — the blackhole entry is the precedent, already written.

Unblocks
The entire rest of the Windows port, within days rather than months.
Cost
Users install a third-party driver. Free VB-CABLE gives one cable; two directions need the paid A+B pack or VAC. Redistribution requires a licence agreement.
Watch for
Device labels differ from Meetron: …, so the label-prefix match in prepare-chatgpt-live.mjs must become configurable rather than hardcoded.
Option B

Driverless in-browser audio bridge

Strategic target

Delete the virtual device from the design entirely. Both tabs already live in one dedicated Chrome profile with the Meetron extension loaded and message passing working. Connect them with an in-browser RTCPeerConnection loopback, signalled through the extension's service worker, and hand each tab the other's track.

The hooks this needs already exist. prepare-chatgpt-live.mjs:239 overrides getUserMedia to pin a device ID; it would instead return the loopback track. setSinkId is already intercepted on <audio> elements and AudioContext; it would instead route into a MediaStreamAudioDestinationNode. This is a change of source, not a change of architecture — and it would simplify macOS too.

Wins
No driver, no kernel code, no EV certificate, no attestation signing, no admin rights, no reboot. Removes the largest install-friction item on both platforms.
Risks
WebRTC processing on the meeting side may mangle synthetic speech — the injected constraints must set echoCancellation, autoGainControl and noiseSuppression to false. Background-tab throttling. ~20–40 ms added latency. Zoom Web's WASM audio path may not go through the standard getUserMedia at all.
De-risk by
Prototyping it on macOS first, where the current device path still works as a control. A two-day spike answers the Zoom question before any Windows commitment.
Option A

Build a Windows kernel audio driver

Last resort

An ACX driver on Windows 11, or a PortCls/SysVAD-derived driver for Windows 10, exposing the same two loopback endpoints. This is the literal translation of what exists today, and it is the only option that leaves the page-level code byte-for-byte identical.

Cost
Kernel C, the WDK, Driver Verifier, HVCI and Secure Boot compatibility, a Partner Center hardware account, an EV certificate, attestation signing per driver revision, and a servicing obligation for every Windows release.
Blast radius
A bug is a bugcheck, not an exception. This is a different class of liability from anything currently in the repo.
Prerequisite
A legal entity that can hold the Partner Center account. This is a business decision, not an engineering one.

Recommendation. Ship Phase 1 on Option C so the whole stack can be validated on real Windows hardware immediately. Run the Option B spike in parallel on macOS. Commit to Option A only if the spike proves the driverless bridge cannot carry Zoom Web — and treat that commitment as a funding decision, not a sprint.

06

Architecture decisions

Direct answers to the five options you raised.

Q1 Shared cross-platform core with thin platform adapters?

Yes — and the seam already exists. definePlatformAdapter() validates a real interface today; it just carries two fields. Grow it to eight capability groups: paths, chrome, process, net, fsSecurity, nativeHost, audioControl, shortcuts. Keep it thin — the adapter answers questions and performs primitive operations; it never contains product logic.

Q2 Separate browser/Chrome functionality from OS-native functionality?

Already done — formalise and enforce it. Everything under src/ except src/platform/<os>/ is browser and protocol code with no OS calls. The rule to write down: only src/platform/<os>/ may import child_process or reference an OS path. There are exactly four violations today, all in scripts/*.mjs, and a lint rule can hold the line afterwards.

Q3 Explicit abstraction layers for capture, permissions, tray, window management…?

Only for what is actually used. Build abstractions for audio devices, Chrome launching, process control, port ownership, filesystem security, native-host registration and Node discovery — all seven have two real implementations, so the abstraction earns its keep.

Do not build one for screen capture (it goes through CDP, never the OS) or for window management (Meetron owns no native windows today). For tray, notifications, hotkeys and autostart, an abstraction with one implementation is speculative generality — write them Windows-only until macOS actually needs them.

Q4 Reuse rather than rewrite?

Reuse aggressively — with one deliberate rewrite. 5,916 lines move untouched. The 3,082 lines of bash should be ported to Node, not PowerShell: Node is already a hard dependency, the orchestration logic in session-launch.mjs is already Node, and a PowerShell port would create a third implementation to keep in sync forever. Porting to Node lets macOS and Windows share one implementation and deletes the bash outright.

Q5 Use modern Windows APIs where they give a better experience?

Yes, in five specific places. Job Objects for process cleanup (strictly better than the current signal dance). Windows Credential Manager for the unimplemented credential store. MMDevice for enumeration. Toast notifications and a tray icon for session state. MSIX for install, uninstall and startup registration. Each is a place where the native API is genuinely better than the portable alternative, not a place where "native" is being used decoratively.

07

What "native Windows" actually means here

Worth stating plainly: there is no native macOS application to wrap. Meetron's UI today is a Chrome extension popup, an injected page panel, and two double-clickable .command shell scripts. So "make it feel native on Windows" is not a porting problem — it is a chance to build the shell that macOS never had, and to let Windows lead.

The Chrome extension should stay exactly as it is. It is the right place for in-meeting controls, because that is where the user's attention already is. What Windows adds is everything that belongs outside the browser:

Native surfaceAPIWhy it earns its place
System tray iconShell_NotifyIcon / WinUI 3Session state at a glance — connected, GPT muted, Voice active — without opening a browser tab. Replaces polling the extension popup.
Toast notificationsAppNotificationManager (needs an AUMID, which MSIX provides)"GPT-Live was admitted", "Voice stopped unexpectedly". Today these failures are silent unless the panel is on screen.
Global hotkeyRegisterHotKeyMute the GPT participant instantly from any window. This is the single most requested control and it currently requires switching to the meeting tab.
Setup & diagnostics windowWinUI 3 / Windows App SDK, Mica backdropReplaces the .command files and the popup wizard with a real settings surface: audio devices, ChatGPT project, permissions, logs.
Start at logonMSIX StartupTask, or Task SchedulerThe host must be reachable when Chrome first sends a Native Messaging request. A per-user startup task — not a Windows service, which has no user session and therefore no audio.
Credential storageCredential Manager / DPAPIFills the credential-store-contract.mjs interface that has no implementation on either platform.

For the shell itself, WinUI 3 on the Windows App SDK gives the most authentically native result — Mica, proper theming, real toast identity — at the cost of a C# toolchain alongside Node. Tauri 2 on WebView2 is the lighter alternative that keeps the UI in JS. Electron would be the fastest to build and the least native-feeling; given the brief explicitly asks for a real Windows application rather than a wrapper, I would not choose it.

08

Phased roadmap

Phases are strictly sequential in their dependencies, though Phase 3's spike and the certificate procurement for Phase 4 should both start early and run alongside.

P0

Widen the seam — macOS only, zero Windows code

The refactoring that must happen before any Windows code is written. Every change here is behaviour-preserving on macOS and independently reviewable.

  • Grow platform-contract.mjs from 2 fields to the 8 capability groups. Update assertResolvedPlatformPaths to accept non-POSIX absolutes.
  • Move the four OS leaks out of scripts/*.mjs: /bin/ps, lsof, process.kill(-pid), and the hardcoded audio-control executable paths.
  • Port scripts/*.sh to Node modules under src/, keeping the same CLI contracts and exit codes (PREPARATION_EXIT_CODES is load-bearing). Delete the bash.
  • Make the audio device label match configurable instead of hardcoded to the Meetron:  prefix.

Exit  npm test green on macOS with no user-visible change; getPlatformAdapter("win32") still throws; no child_process import outside src/platform/.

P1

Windows bring-up on a third-party cable

First real end-to-end session on Windows 11. Deliberately ugly — no native UI yet, setup done by hand.

  • src/platform/windows/ implementing all eight groups; register it in platform-registry.mjs.
  • meetron-host.exe shim + registry-based Native Messaging registration.
  • Job Object process control; Get-NetTCPConnection-equivalent port ownership check; ACL-based secureFile().
  • meetron-audioctl.exe over MMDevice, emitting the existing JSON contract.
  • New vb-cable entry in AUDIO_BACKENDS.
  • Add windows-latest to the CI matrix; package.json os becomes ["darwin","win32"].

Exit  A Google Meet session runs end to end on Windows 11: GPT-Live joins, two-way audio works, screen send works, session stop cleans up with no orphaned Chrome. Zoom Web validated separately.

P2

The native Windows shell

Turn a working port into an application. This is where the Windows build stops looking like a Mac tool.

  • WinUI 3 app: tray icon with live session state, setup and diagnostics window, settings.
  • Toast notifications for admission, Voice failure and session end.
  • Global hotkey for GPT participant mute.
  • Credential store over Credential Manager — first implementation of that contract on any platform.
  • Microphone-privacy preflight with a deep link into Settings.

Exit  A user can install, configure and run a meeting without opening a terminal or reading the README.

P3

Driverless audio bridge

Remove the third-party driver dependency. Spike starts during P0 on macOS; productionised here.

  • WebRTC loopback between the ChatGPT and meeting tabs, signalled through the extension service worker.
  • Rewire the existing getUserMedia and setSinkId hooks to source from the loopback instead of a device ID.
  • Validate against Google Meet and Zoom Web independently — Zoom is the risk.
  • Ship behind a backend flag; promote to default only after it holds on both providers.

Exit  A clean Windows machine with no audio driver installed runs a full session. Latency and audio quality measured against the cable backend, not assumed.

P4

Packaging, signing and updates

Certificate procurement should have started during P1 — lead time, not build time, is the constraint.

  • MSIX package with bundled Node runtime and a startup task.
  • Authenticode signing on an HSM-backed certificate; sign the beta too, so SmartScreen reputation starts accruing early.
  • Windows equivalents of setup-meetron.sh / update-meetron.sh, preserving the existing "detect the live install and update in place" behaviour.
  • Release pipeline mirroring package-community-release.sh, with checksum and signature verification.

Exit  A signed installer downloads and runs on a clean Windows 11 machine without a SmartScreen block, and updates in place without losing the Chrome profile or login state.

P5

Own kernel audio driver — conditional

Only if P3 proves the driverless bridge cannot carry Zoom Web or meets an unacceptable quality bar. Do not start speculatively.

  • Partner Center hardware account, EV certificate, attestation signing pipeline.
  • ACX driver for Windows 11 exposing two loopback endpoints; PortCls fallback if Windows 10 must be supported.
  • The 149-line ring buffer is conceptually reusable but must be rewritten against Interlocked* for kernel mode.
  • MSI wrapper with pnputil driver install; Driver Verifier and HVCI validation.

Exit  Attestation-signed driver installs without a reboot and presents both endpoints. Treat this phase as a funded project, not a sprint.

The dependency that matters: P0 gates everything, and it is entirely macOS work. It is also the phase most likely to be skipped under schedule pressure — and skipping it produces a forked codebase where every future feature is written twice.

09

Risks worth naming now

RiskWhy it bitesMitigation
Zoom Web resists the driverless bridge
High impact		 Zoom is already the fussiest provider — prepare-zoom.mjs is 729 lines of workarounds, and the code comments note it bypasses setSinkId hooks on reinitialise. Its WASM audio path may not use standard getUserMedia at all. Spike Zoom first, on macOS, during P0. It is the cheapest way to learn whether Option B is viable, and it decides whether P5 is on the roadmap.
Silent loss of file permissions
Security		 Node accepts {mode: 0o600} on Windows and ignores it. The .env holds the ChatGPT project URL and runtime state; nothing will fail, and nothing will warn. Make secureFile() mandatory in P1 and add a test that asserts the resulting ACL, not just that the write succeeded.
Orphaned Chrome processes
Reliability		 The macOS cancel path relies on process-group signals. A naive Windows port using taskkill /PID without /T leaves the Chrome tree running and the CDP port occupied — and the next launch then fails its ownership check. Job Object with KILL_ON_JOB_CLOSE from the start. Test the host-crash path explicitly, not just the clean-stop path.
Antivirus and SmartScreen false positives
Distribution		 A Native Messaging host that spawns detached processes, opens a local debug port and injects scripts into pages is a textbook heuristic match. Unsigned, it will be quarantined on some machines. Sign from the first beta. Submit to Microsoft for false-positive review early. Budget for it — it is not a one-off.
Path handling
Low		 Profile paths under %LOCALAPPDATA% contain spaces, and the current process match does substring comparison on --user-data-dir=… --no-first-run. Deep Chrome profile trees can also hit MAX_PATH. Quoting-aware command-line parsing; keep the profile directory shallow; enable long paths in the installer.
Bash port regressions
Medium		 3,082 lines of shell encode real behaviour — exit-code contracts, in-place update detection, backend auto-detection. tests/scripts-test.sh covers some of it, and it too is bash. Port the tests to Node alongside the scripts, one script at a time, keeping both implementations alive until the Node one passes the existing test.
Third-party cable licensing
Legal		 VB-CABLE is donationware; bundling or redistributing it needs a licence agreement. Meetron is GPL-3.0, which constrains what can be shipped alongside it. Detect and instruct rather than bundle, mirroring how BlackHole is handled today. Get the licence question answered before P1 ships publicly.
10

Decisions needed before Phase 1

Four questions I cannot answer from the codebase. Each one changes the plan materially.

Is there a legal entity that can hold a Partner Center hardware account and an EV certificate?

If not, Option A is off the table entirely and Option B stops being the preferred path and becomes the only one. This changes P3 from "strategic improvement" to "critical path" and should be scheduled accordingly.

Is a third-party driver dependency acceptable for the Windows beta?

The BlackHole precedent says yes, and it is what makes a Windows build possible in weeks rather than quarters. But it is a visibly worse first-run experience than the current macOS .pkg, and it needs a licensing answer.

WinUI 3 with a C# toolchain, or Tauri/WebView2 staying in JavaScript?

WinUI 3 is more authentically native and gives toast identity and Mica for free; Tauri keeps one language across the project. This decides P2's shape and who can work on it.

Does Windows ship in the OSS Community edition, or only in a commercial build?

The README currently lists a Windows version alongside notarized apps and auto-update as explicitly out of scope for the OSS release. If that stays true, the platform adapter still belongs in this repo — but the installer, shell and signing pipeline live elsewhere, and P0 should be designed to keep that split clean.
